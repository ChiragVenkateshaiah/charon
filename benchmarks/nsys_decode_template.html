What this shows

The top lane is the CPU: one grey tick per cudaLaunchKernel. The bottom lane is the GPU: one coloured block per kernel, with hatching where it is idle. The thin lines join each launch to its kernel. Look at three things. First, the CPU lane is never empty, so the CPU is always busy. Second, the GPU lane is mostly hatched. Third, the joining lines are almost vertical, so each kernel starts the moment it is launched. Nothing waits in a queue. The GPU runs one tiny kernel in 1–3 µs, then waits for the CPU to send the next. Only the long blue GEMVs let the CPU get a few kernels ahead. The dashed lines mark token boundaries. Every token has the same shape.

What this shows

Every layer looks the same. About 1.37 ms of wall time holds only about 0.45 ms of GPU work, and most of that is the seven GEMV projections (q, k, v, o, gate, up, down). The setup block is almost all waiting: 64 tiny kernels for logits processing, argmax and bookkeeping take about 1.57 ms of wall but about 0.12 ms of GPU time. Only the LM head is solid, because it is one long kernel (about 1.83 ms) and the GPU has nothing to wait for. The kernel strip on the right shows why a layer idles: 33 of its 40 kernels are tiny (orange, aqua, magenta, green), and the host needs about 28 µs to send each one.

What this shows

Left: the two histograms barely overlap. Most kernels run in 1–3 µs (median 1.7 µs), but the CPU sends one about every 28 µs (median). When the work is shorter than the delivery interval, the GPU must wait, and that is most of the time. Right: the decode thread spends about 9.7 ms per step inside CUDA calls and about 32.2 ms outside them. Each launch call takes about 7 µs of the 28 µs interval. The larger part is host work outside the CUDA runtime: Python and the PyTorch dispatcher Inferred. Which of these is larger is Unknown, because the VM refused CPU sampling. The profiler stretches these CPU times, so read this as a direction, not a size.

E · Top kernels

Two GEMV kernels do 87% of the GPU work

Share of GPU kernel time inside the 3,810 decode steps. Hover a bar for the exact Nsight name. Measured

Table with exact kernel names
What this shows

The two cuBLAS gemvx kernels are the weight projections. Variant 6 runs q, o, gate, up and the LM head; variant 7 runs k, v and down. Together they are 87% of GPU time. The other eight entries are tiny elementwise kernels that each run 1–3 µs but are called about 56–112 times per token. They cost little GPU time but a lot of launches, which is the pattern from section C. If a kernel profiler is used later, the two GEMV variants are where to look.

A longer one (about 228 µs median) comes at the token boundary, where the CPU waits for the LM head to finish and reads the new token back Inferred. H · Roofline connection

The kernels come close to the bandwidth roof; the GPU just runs them rarely

Weight bytes from the Qwen2.5-1.5B config, divided by each GEMV's measured duration. Derived. This is not measured DRAM bandwidth.

What this shows

While a big GEMV runs (gate, up, down, LM head), it streams weights at about 250 GB/s, near the L4's 300 GB/s datasheet limit. The small k and v projections reach less, because they are too short to get up to speed. The roofline's 106.5 GB/s average is lower only because the GEMVs run less than half of each token. The bottom bar shows the arithmetic: about 247 GB/s while running, times about 43% of the time running, gives about 106 GB/s. So the 35.5% roofline gap is mostly a duty-cycle effect, caused by the host. Nsight Compute is needed to confirm the per-kernel bandwidth with real counters.

I · Hypotheses and decision

What limits decode, and what to measure next

1

D · CPU/Python orchestration

high that the host sets the pace · medium on how its time splits
  • For: the GPU is idle about 66% of each profiled step, in about 1,197 small gaps. GPU-busy time is constant while wall time varies. 73% of kernels start within 5 µs of being launched. The host sends a kernel about every 28 µs, but only about 7 µs of that is inside the launch call.
  • Against or gaps: no CPU stacks, so the split between Python and the PyTorch dispatcher is unknown. The profiler stretches host time.
2

C · Kernel launch overhead

medium
  • For: about 1,194 launches per token, each a real 7–9 µs call, about 9.7 ms per step inside CUDA calls.
  • Against: it is the smaller part of each 28 µs launch interval, and the profiler inflates exactly this call.
3

B · Memory bandwidth, inside the GEMVs only

medium-low
  • For: GEMVs are 87% of GPU time, and the big ones reach about 250 GB/s (derived), roughly 83–85% of datasheet.
  • Against: derived, not measured, and it covers only the third of the step when the GPU is busy.

Not ranked: compute (AI ≈ 1, almost no arithmetic), synchronization (about 0.5% of a step), occupancy (unknown without Nsight Compute). The trace does not show Charon as memory-bound or compute-bound as a whole.

Nsight Compute next? Not yet.

About two-thirds of each profiled token is the GPU waiting on the host, and Nsight Compute only explains the busy third. First, repeat this Nsight Systems trace with CPU sampling enabled. That needs a VM setting changed, with your approval, and about 0.4 GPU-hours (estimated, not measured). It finds who owns the roughly 20 µs per kernel outside the launch call. Then run Nsight Compute on gemvx (int)6 (the gate/up instance and the LM-head instance) and gemvx (int)7 (the down instance). Collect achieved DRAM bandwidth, memory throughput and L2 hit rate, occupancy, SM throughput, warp stall reasons, FLOP throughput and the roofline chart.
